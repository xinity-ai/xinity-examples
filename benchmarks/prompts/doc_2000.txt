Section one, background. Modern large language model inference servers are organised around two distinct phases of work. The first phase is prefill, during which the server reads the input prompt, computes the key and value tensors for each layer of the model, and stores them in a cache. The second phase is decode, during which the server generates output tokens one at a time, reusing the cached prefill state and appending the new token at each step. Prefill is heavy in compute and tends to be limited by matrix multiplication throughput, while decode is heavy in memory bandwidth and tends to be limited by the rate at which the device can stream weights and the growing key value cache. The relative cost of these two phases depends on the hardware, the model, and the lengths of the input and output. As a result, two requests with the same total token count can take very different amounts of time depending on how the tokens are split between prompt and generation. A request with a long prompt and a short generation will be dominated by prefill, while a request with a short prompt and a long generation will be dominated by decode. A reasonable benchmark therefore measures TTFT and decode throughput separately, so that the cost of each phase is visible.

Section two, observed behaviour at single concurrency. When a single request is sent to such a server with a short prompt and a long generation, almost all of the wall clock time is spent in decode. The time to first token is small, because prefill on a short prompt finishes quickly. The total request time is dominated by the cost of producing each output token. The throughput of the generation, measured in output tokens per second, is roughly the inverse of the per token decode time. When the same server is sent a long prompt and a short generation, the time to first token grows because prefill on a long prompt is heavier. The total request time is dominated by prefill rather than by decode, and the average tokens per second over the whole request can be misleading if it includes the prefill phase. For this reason it is common to report TTFT and decode throughput as separate numbers, where decode throughput is computed only over the streaming portion of the response. A practitioner who only looks at total request time will not be able to tell whether a slow result was caused by long prefill or by slow decode, which limits the diagnostic value of that single number.

Section three, concurrency. When more than one request is in flight at the same time, the server interleaves their decode steps. With efficient batching, each new concurrent request adds only a small overhead per decode step, so the total tokens per second across the batch grows roughly in proportion to the number of requests, up to the point where the device is saturated. Past that point, additional requests no longer add throughput and instead increase the latency per request. The shape of this curve is a useful summary of how a server behaves under load. A benchmark that steps through a sequence of concurrency levels, holding the prompt size constant, can be used to find the inflection point at which the server stops scaling and starts to slow down. Servers that implement continuous batching tend to scale further than servers that implement static batching, but every server has a saturation point, and that point is where capacity planning decisions are usually anchored. A second effect of high concurrency is that the time to first token grows, because new requests must wait for a free batch slot or for the running batch to admit them.

Section four, prompt size. Prompt size also matters. A long prompt occupies more space in the key value cache and more bandwidth at every decode step. As prompt size grows, the per token decode time on the same server tends to increase, because the attention computation reads from a larger cache. As prompt size grows, the time to first token also increases, because prefill scales roughly linearly with prompt length up to the limits of the attention implementation. Benchmarks that compare different prompt sizes at the same concurrency level can reveal how a server handles long contexts and where the cost of long prompts begins to dominate the response time. Some servers implement chunked prefill or paged attention, which softens the impact of long prompts on TTFT but does not eliminate it. Reporting TTFT at several prompt sizes is therefore a more honest summary than reporting a single TTFT number on a short prompt.

Section five, measurement notes. To produce a reliable measurement, it is important to use a monotonic clock such as time perf_counter rather than wall clock time, to discard a warm up request before recording any results, and to count output tokens using the usage information provided by the server when available. When the server reports usage as part of the streaming response, the resulting tokens per second number is grounded in the same tokenizer that the server itself uses. Without the usage block, output tokens must be approximated, for example by counting non empty content chunks. This approximation tends to undercount because servers sometimes pack multiple tokens into a single chunk, and tends to overcount on whitespace heavy outputs. The recommended approach is to set the include usage flag in the streaming options and to fall back to chunk counting only when the server does not honour that flag. A further hygiene rule is to share a single connection pool across all concurrent requests, so that benchmark numbers are not distorted by repeated TLS handshakes or by transient DNS lookups during the measurement window.

Section six, statistics. Single number summaries are convenient but lossy. A sensible benchmark reports both a mean and a tail value such as p95 for each metric, so that users can see whether a server is stable under load or whether a small fraction of requests are much slower than the rest. The mean captures average behaviour, while the tail captures the worst case experience that a real user might see when traffic is at its peak. For a streaming endpoint, the most informative tail is the TTFT p95, because it tells the operator how often a user has to wait an unusually long time before the first token appears. The decode throughput tail is generally less interesting, because the difference between the median and the worst case decode rate is often small once a request has reached the streaming phase.

Section seven, repeatability. Inference benchmarks that are not repeatable have limited value. Repeatability means that the same script run on the same server should produce comparable numbers across runs, and that the numbers should reflect the steady state of the server rather than transient effects. The most common sources of run to run variability are cold start effects in the first few requests, network jitter on remote endpoints, autoscaling of underlying compute, and changes in concurrent traffic from other users sharing the same backend. A well behaved benchmark addresses each of these. Cold start is mitigated by a warm up request that is excluded from the recorded results. Network jitter is mitigated by running the script on a host that is close to the server and by reporting both mean and p95 so that the reader can see the spread. Autoscaling effects are mitigated by running each concurrency level for long enough that the autoscaler has stabilised before the measurement is taken. Cross traffic effects can only be reported, not eliminated, and a careful operator should note in the surrounding text whether the benchmark was run on a dedicated deployment or on a shared one.

Section eight, output tokens as a measured variable. In some benchmarks the maximum output length is fixed at a small number such as 256 tokens, so that throughput numbers can be compared cleanly across deployments. In other benchmarks the output length is left unbounded and is itself reported as an outcome, on the grounds that the natural response length of the model is part of what users actually experience. Both choices are defensible. When output length is fixed, throughput numbers are a clean measurement of decode speed, but they no longer reflect the response that a user would actually receive. When output length is unbounded, the reported tokens per second include the model's tendency to write longer or shorter answers, which is informative on its own but can complicate apples to apples comparisons between models. The choice should be documented in the benchmark output so that readers can interpret the numbers correctly.

Section nine, summary. A useful benchmark is one that holds as many variables constant as possible and varies a small number of dimensions in a controlled way. The two natural dimensions for an inference benchmark are concurrency, which probes how the server scales under load, and prompt size, which probes how the server handles different shapes of work. Together these two dimensions cover a large fraction of what users care about in practice. The resulting tables are easier to interpret if each row corresponds to a single concurrency level at a single prompt size, and if each metric is reported with both a mean and a tail value such as p95 to capture variability across requests. When the same benchmark is rerun against several model deployments, the resulting tables form a compact comparison that can guide both model selection and capacity planning.
